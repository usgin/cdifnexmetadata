# exampleMetadata — CDIF documents generated from `exampleData/`

Outputs, not fixtures. Regenerate with:

```bash
python exampleMetadata/generate.py --profile-dir ../XAS-CDIF/release
```

`generate.py` names no crosswalk for any of these. The mapper reads the
application definition each file declares and picks one itself, which is
why the XAS and SAS examples can sit in the same list. The documents are
byte-identical to those produced when the crosswalk was passed by hand.

| `NXmx-Therm_6_2.jsonld` | 1 | 2 | 0 | core, discovery |

*Concepts* is the count for the richest single entry; *variables* is
`schema:variableMeasured` on the document.

## What to look at in each

**`FeXAS.jsonld`** is the fullest example and the only one validated
end to end. Worth reading for:

- the **archive-of-parts** shape — one `schema:Dataset`, one
  `schema:DataDownload`, and 26 `schema:MediaObject` parts, each
  referencing a shared `cdi:DimensionalDataStructure` by `@id` rather
  than repeating it;
- **two** structures, not one: `FeFoil.001` carries a transmission
  detector the 25 sample scans do not;
- `schema:description` on properties read from a **non-standard layout**,
  naming the `gsecars-athena` convention that put them there;
- `cdif:LocatorMapping` with `cdif:locator` holding the HDF5 internal
  path — a locator, not a column index.

**`APS-USAXS-pinSAXS.jsonld`** is the second technique, produced with no
code change beyond passing a different crosswalk. Its four variables all
come from the legacy path table, because this writer leaves
`NXdetector/data` empty and stores the image in `NXdata` as `frames`.

**`NXsas-autogenerated.jsonld`** maps 24 concepts and yields **zero**
variables — every array in the source is a placeholder scalar, so there
is nothing measured to describe. A useful reminder that concept count and
data description are different things.

**`NXmx-Therm_6_2.jsonld`** and **`NXtomo-autogenerated.jsonld`** are
thin on purpose: no crosswalk covers macromolecular crystallography or
tomography, so only base-class concepts map. This is what an unsupported
technique looks like.

**`cu_metal_rt.jsonld`** is a single-spectrum XAS document — the same
technique as `FeXAS.jsonld` without the archive-of-parts machinery, so
it is the smaller thing to read first if the 26-part file is too much.

**`cu_metal_10K.jsonld`** is the only document here that **fails**
validation, and it should. Its source declares `NXxas` and then carries
almost none of it, so there is no detection mode to report; the profile
requires one. The failure is the extractor refusing to invent a value,
which is the behaviour worth having an example of.

## On validation

Three documents are validated here against the `xasDocument` composite:
`FeXAS` and `cu_metal_rt` pass, with advisory SHACL results for things a
NeXus file genuinely does not record (a creator, a contact point, an
instrument category from a controlled vocabulary). `cu_metal_10K` fails,
for the reason above.

The other four are reported `n/a` rather than validated. Running a SAS or MX
document against the XAS profile would produce a long list of failures
that mean nothing, since those documents never claimed to satisfy it —
and **"not applicable" and "failed" are different answers**. When a SAS
profile exists, `generate.py` should check against it.

## A caveat on identifiers

Every `@id` and `schema:contentUrl` here is under
`https://w3id.org/cdif/testing/`, which does not currently resolve.
These are examples, not published records; a real deployment passes
`--base` and `--source-url`.
