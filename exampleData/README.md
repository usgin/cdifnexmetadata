# exampleData — the NeXus files the examples are generated from

Eighteen HDF5 files, chosen to span what the extractor actually meets
rather than to flatter it. All but one are copied unmodified from a
public NeXus example collection; `NXxas-manual-sketch.hdf5` is built
here, and says so below. `exampleMetadata-NEXUS/` holds the CDIF
document generated from each, and `exampleMetadata-NEXUS/generate.py`
regenerates them.

| File | Size | Definition | Why it is here |
|------|------|-----------|----------------|
| `FeXAS.nxs` | 2.6M | `NXxas` | 26 `NXentry` groups — the archive-of-parts case. The only example that validates against a full CDIF profile. |
| `APS-USAXS-pinSAXS.hdf5` | 1.9M | `NXsas` | A real beamline file that departs from its own declared definition. |
| `NXsas-autogenerated.hdf5` | 39K | `NXsas` | Generated *from* the definition, so it follows it exactly. The contrast with the file above is the point. |
| `NXmx-Therm_6_2.nxs` | 65K | `NXmx` | Macromolecular crystallography. No crosswalk covers it. |
| `NXtomo-autogenerated.hdf5` | 30K | `NXtomo` | Tomography. Likewise uncovered. |
| `cu_metal_rt.nxs` | 64K | `NXxas` | A clean single-spectrum XAS file — the counterpart to FeXAS's 26-entry archive. |
| `cu_metal_10K.nxs` | 31K | `NXxas` | Declares `NXxas` and is nearly empty. Included because it *fails*. |
| `NXxas-manual-sketch.hdf5` | 22K | `NXxas` | **Built here, not copied.** The layout the NeXus manual sketches, which no real file uses. Included because it *misses*. |
| 10 × `*_rt.nxs`, `feo_rt1.nxs` | 57–60K each | `NXxas` | The same measurements this project already holds as XDI, in NeXus. Included so the two encodings can be compared on identical data. **Rights unresolved — see below.** |

## Why the uncovered ones are included

`NXmx-Therm_6_2.nxs` and `NXtomo-autogenerated.hdf5` produce thin
documents: base-class concepts only, no variables, `core` and `discovery`
and nothing more. That is not a defect being hidden — it is what an
unsupported technique looks like, and it is here so the gap can be read
directly instead of inferred from a claim that everything works.

Adding a technique is a crosswalk, not a code change. These two files are
what that sentence costs when nobody has written the crosswalk yet.

## Why a broken file is included

`cu_metal_10K.nxs` declares `NXxas` and then carries almost none of it:
no `NXdata`, no `NXsample`, no scan group, and an `i0` detector with no
`data` in it. It is not corrupt — it reads fine — it is simply thin.

Its document is the only example that **fails** validation, and it fails
for the right reason: the profile requires a detection mode, the file
does not record one, and the extractor says so instead of inventing it.
An examples directory where everything passes tells you nothing about
what happens when something is wrong.

### Rights on the Newville files are unresolved

The thirteen files from `millenia.cars.aps.anl.gov/nxxas/` — the ten
added on 2026-07-28 plus `FeXAS.nxs`, `cu_metal_rt.nxs` and
`cu_metal_10K.nxs` — carry **no stated data licence**. The site footer
says only "© Copyright 2023, Matthew Newville".

They are therefore absent from `REUSE.toml` on purpose. REUSE reads an
unannotated file as *unknown*, which is true; a guessed copyright line
would not be. Resolving this needs a word with Newville, and one answer
covers all thirteen.

## The same measurements in two encodings

Ten of the single-spectrum files have a counterpart in
`XAS-CDIF/exampleData/` with the same base name — `co_metal_rt.nxs`
against `co_metal_rt.xdi`, and so on. Same spectra, same instrument,
different encoding, which isolates the format from the content: any
difference in the CDIF output is attributable to the encoding and its
binding rather than to the data.

Measured over the ten, neither encoding dominates:

| | concepts | provides what the other does not |
|---|---|---|
| NeXus | 15 | `monochromatorchemicalformula`, from `NXcrystal/chemical_formula` |
| XDI | 16 | `samplepreparation` (`Sample.prep`) and `monochromatortype` (`Mono.name`) |

`feo_rt1` inverts it — 14 from NeXus against 12 from XDI, because its
NeXus version records a facility and an x-ray source type that its XDI
header omits.

The ten are **not registered in `exampleMetadata-NEXUS/generate.py`**.
They are near-identical single-spectrum files, and adding all ten would
roughly double the generated example set to make a point two of them
already make.

## Why a file nobody wrote is included

`NXxas-manual-sketch.hdf5` is the one file here that is not real data.
The NeXus definitions repository ships **no XAS example files at all** —
the ten HDF5 files under `manual/source/examples/` declare no
`definition` and contain only generic classes, and the three XAS
branches add none. The only record of an XAS file layout in that
repository is a 30-line structure sketch,
`manual/source/examples/xas.txt`.

That sketch differs from every real file here in two ways, and
`tools/make_nxxas_manual_example.py` builds a file that follows it so
those differences can be measured instead of argued about:

| | the sketch | every real file here |
|---|---|---|
| monochromator | directly under `NXentry` | under `NXinstrument` |
| detectors | `I`, `I0` | `itrans`, `i0` |

The result: **2 concepts mapped, against 15 for `cu_metal_rt.nxs`.**
Most of that gap is simple absence — the sketch has no facility,
beamline, element or edge — but two concepts are *present in the file
and still missed*:

- `monochromatorenergy`. The crosswalk states
  `/ENTRY:NXentry/INSTRUMENT:NXinstrument/monochromator:NXmonochromator/energy`;
  an entry-level `monochromator` cannot satisfy a path that requires an
  `NXinstrument` segment.
- `transmittedintensity`. The crosswalk expects `itrans:NXdetector`, and
  `I` is nothing like it.

`incidentintensity` *is* found, because `I0` matches `i0`
case-insensitively. That asymmetry — one detector recovered, its pair
lost — is the clearest illustration in the corpus of what naming
conventions cost.

Its document fails validation with 4 errors, for the same reason
`cu_metal_10K.nxs` does: the profile requires an absorption edge, a
target element and classified instrument peers, and the file records
none of them.

One of the two is now in `data/legacy-paths.tsv`, under the convention
`nexus-manual-sketch`, and the file maps 3 concepts rather than 2.

The other **cannot be expressed there**, which is the more useful
finding. Legacy paths use NXDL syntax, where an uppercase segment name
means "any instance of this class" — so `I:NXdetector` matches every
detector in the entry, not the one named `I`. Adding that row made
`transmittedintensity` resolve to *both* `I` and `I0`, writing the
incident beam into the transmitted concept, and it broke two emit tests
by attaching itself to every fixture that has any detector. It was
removed; `legacy-paths.tsv` records why at the top.

So a writer that names detectors in capitals is beyond what the path
syntax can describe. Nothing here needs that today, and the constraint
is now written down rather than waiting to be rediscovered.
